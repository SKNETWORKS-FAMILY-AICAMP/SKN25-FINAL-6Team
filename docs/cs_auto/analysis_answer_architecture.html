CS Auto Architecture

analysis agent와 answer agent를 분리한 현재 구조는 성능 최적화와 운영 통제라는 두 목적에 맞는 시스템 설계다

apps/cs_auto 기준으로 보면, 시스템은 문의를 먼저 분석하고 (ticket_analysis), 그 결과를 바탕으로 필요한 근거만 조회해 답변 초안(answer_draft)을 생성한다. 이 분리는 단순한 역할 분담이 아니라 LLM 호출량, DB/문서 조회 비용, 재처리 범위, 운영자 검수 흐름을 분리해 전체 운영 난도를 낮추는 구조다.

01:00 KST 분석 배치
04:00 KST 초안 생성 배치
분석 결과와 초안 이력 분리 저장
운영자 수정 · 재생성 · 승인 API 분리
1

티켓 수집

qa_ticket에서 아직 분석되지 않은 문의를 읽는다.

구현 근거: analysis_agent.fetch_unanalyzed_tickets()

2

분석 선행

카테고리, 감성, 위험도, 라우팅 타깃을 산출해 ticket_analysis에 저장한다.

구현 근거: build_analysis_result(), save_ticket_analysis()

3

답변 생성

분석 결과의 routing_target에 따라 DB, 문서, 복합 조회 중 필요한 경로만 실행한다.

구현 근거: AnswerEvidenceCollector.collect()

4

운영 검수

초안, 근거, safety 결과를 보고 운영자가 수정, 재생성, 승인, 메일 발송을 수행한다.

구현 근거: /api/cs-auto/tickets/*, approve_draft.py

Performance View

성능 관점에서 맞는 이유

  • 모든 티켓에 무조건 DB 조회와 문서 검색을 동시에 태우지 않는다. 먼저 분석해서 DB_only, doc_only, DB&DOC, fixed_answer로 좁힌 뒤 필요한 경로만 호출한다.
  • 분석 결과를 저장해 두기 때문에 초안 재생성 시 분류를 다시 하지 않아도 된다. 운영자가 문안만 다시 뽑고 싶을 때 재처리 범위가 작다.
  • 분석 단계는 비교적 짧고 구조화된 판단 작업이고, 답변 단계는 검색과 생성이 섞인 무거운 작업이다. 둘을 분리하면 배치 시간대를 다르게 잡아 피크를 분산할 수 있다.
  • 근거 수집이 analysis_agent가 아니라 answer_agent에만 있으므로, 분석 배치는 대량 티켓 선별용으로 가볍게 유지된다.
  • fixed_answer 경로를 두어 짧은 잡담성 문의나 컨텍스트 부족 문의에서 고비용 조회와 긴 생성 단계를 우회한다.
Operations View

운영 관리 관점에서 맞는 이유

  • 운영자는 원문을 바로 읽는 대신 분석 요약, 위험도, 라우팅 판단을 먼저 본다. 대기열 우선순위 결정이 쉬워진다.
  • answer_draft, evidence_docs, safety_results, final_response가 분리돼 있어 초안 품질, 근거 부착, 최종 승인 이력을 나눠 추적할 수 있다.
  • 초안 승인 API는 최종 답변을 final_response에 저장한 뒤 티켓을 종료한다. 즉, AI 초안과 실제 발송 답변이 구분된다.
  • 재생성 API는 regeneration_reason과 retry_count를 남기는 구조라 운영 피드백을 반복 개선 루프로 연결하기 좋다.
  • 분석 배치와 초안 배치가 Airflow DAG로 나뉘어 있어 장애 시 어느 단계가 병목인지 구분하기 쉽고, 실패 재실행 범위도 명확하다.

역할 분리의 핵심 구조

구성 요소 주요 책임 주요 입력 주요 출력 운영상 의미
analysis_agent.py 문의 정규화, 카테고리 분류, 감성/위험도 평가, 근거 조회 전략 결정 qa_ticket ticket_analysis 생성 이전에 “어떤 문의인가”와 “어떤 근거가 필요한가”를 먼저 고정한다.
answer_agent.py 근거 수집, 초안 생성, safety 평가, fallback 라우팅, 저장 qa_ticket + 최신 ticket_analysis answer_draft, evidence_docs, safety_results 무거운 검색과 생성은 분석 결과를 활용해 필요한 범위로만 실행한다.
approve_draft.py 운영자 확정본 저장 운영자 수정 문안 final_response AI 초안과 실제 고객 발송 문안을 분리해 책임 경계를 명확히 한다.
regenerate_draft.py 운영자 피드백 기반 재생성 기존 draft_id, 재생성 사유 새 draft_id, 새 safety_id 실패 원인을 버리지 않고 다음 생성에 연결한다.
Airflow DAG 2종 배치 분리 실행 스케줄 단계별 자동화 분석 장애와 답변 생성 장애를 별도로 관제할 수 있다.
Why Analysis First

analysis agent의 역할

  • 문의 텍스트를 정규화하고 키워드 + LLM 보조로 카테고리를 분류한다.
  • 위험도와 감성을 먼저 계산해 운영상 긴급성을 분리한다.
  • 핵심은 답변문 생성이 아니라, 이후 단계가 어떤 자원을 써야 할지를 결정하는 것이다.
  • 즉 이 단계는 “답을 쓰는 모델”이 아니라 “처리 전략을 정하는 모델”에 가깝다.
Why Answer Later

answer agent의 역할

  • routing_target에 따라 DB 검색기와 문서 검색기를 선택적으로 실행한다.
  • 수집한 근거로만 초안을 만들고, 이후 safety 평가로 다시 한 번 필터링한다.
  • 점수가 낮으면 자동으로 fixed_answer 문안으로 강등한다.
  • 즉 이 단계는 “생성”보다 “근거 기반 생성 + 안전성 게이트”에 가깝다.
Why Human Last

운영자 검수 단계의 의미

  • 운영자는 초안만 보는 것이 아니라 근거와 safety 맥락까지 함께 본다.
  • 수정 API와 재생성 API가 분리돼 있어, 문장만 다듬을지 근거 포함 재생성할지 선택 가능하다.
  • 최종 승인 시에만 final_response가 생기므로, 발송 책임이 명확하다.
  • 이 구조는 “AI 자동화”가 아니라 “AI 보조 + 운영 통제”를 목표로 한 설계다.

이 구조가 운영 KPI에 유리한 이유

운영 목표 분리 구조가 주는 효과
응답 속도 개선 분석을 선행해 답변 생성 대상을 좁히고, 필요 없는 검색을 줄여 평균 처리 시간을 낮춘다.
고위험 문의 선별 risk_level, sentiment, routing_target이 먼저 만들어져 운영자가 우선 검토 큐를 쉽게 구성할 수 있다.
품질 추적 분석 결과, 근거, 초안, safety, 최종 답변이 분리 저장되므로 어느 단계에서 품질이 떨어졌는지 역추적 가능하다.
비용 통제 모든 티켓에 고비용 생성과 조회를 수행하지 않고, 전략형 분석 결과로 후속 자원 사용량을 제어한다.
실패 복구 분석 단계와 답변 단계가 독립적이라 한 단계만 재실행할 수 있고, 배치 실패 시 영향 범위를 줄일 수 있다.
Code Evidence

현재 코드 기준의 직접 근거

  • apps/cs_auto/backend/airflow/analysis_agent_dag.py: 매일 01:00 KST 분석 배치 실행
  • apps/cs_auto/backend/airflow/answer_agent_dag.py: 매일 04:00 KST 초안 생성 배치 실행
  • analysis_agent.build_analysis_result(): 분류, 위험도, 라우팅 결과를 한 묶음으로 생성
  • AnswerEvidenceCollector.collect(): 라우팅 값에 따라 검색 경로 분기
  • AnswerSafetyEvaluator.evaluate(): 초안 품질을 별도 단계에서 점수화
  • approve_answer_draft(): 운영자 승인 후 final_response 저장 및 티켓 종료
Current Caveat

현재 구현 기준 보완 포인트

구조 자체는 목적에 맞다. 다만 코드 기준으로는 분석 완료 후 상태값이 resolved로 기록되는 부분과 문서/주석에서 설명하는 analyzed 개념 사이에 불일치가 보인다. 운영 관점에서는 상태 머신을 pending → analyzed → draft_generated → resolved 처럼 명확히 통일하는 편이 관제와 통계에 더 유리하다.

관련 위치: analysis_agent.mark_ticket_analysis_completed(), answer_agent.mark_answer_draft_completed(), approve_draft.py

Conclusion

정리

analysis agent는 문의를 이해하고 처리 전략을 정하는 계층이고, answer agent는 그 전략에 따라 근거를 수집해 초안을 만드는 계층이다. 이 둘을 분리했기 때문에 시스템은 빠르게 선별하고, 필요한 곳에만 무거운 생성을 쓰고, 운영자는 결과를 검수하고 재개입할 수 있다.

따라서 apps/cs_auto의 현재 구조는 “LLM을 많이 쓰는 구조”가 아니라 “LLM을 통제 가능한 단계로 쪼개서 성능과 운영 가능성을 확보한 구조”라고 설명하는 편이 정확하다.

작성 기준 파일: apps/cs_auto/backend/agents/analysis_agent.py, apps/cs_auto/backend/agents/answer_agent.py, apps/cs_auto/backend/airflow/*.py, apps/cs_auto/backend/api/services/*.py
